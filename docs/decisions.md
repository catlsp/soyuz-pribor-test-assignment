# Проектные решения и ограничения

## Принципы генерации

Входные данные являются единственным источником технических фактов. Промпт должен явно запрещать модели выводить характеристики, совместимость, сертификаты, наличие, сроки, гарантию или преимущества, которых нет в исходном вводе. Для отсутствующего ожидаемого значения используется точная строка `данных нет`; пропуски дополнительно перечисляются в `missing_fields`.

SEO-заголовок ограничен 70 символами, описание — 800–1200 символами. Поисковые запросы ориентированы на коммерческий B2B-поиск: закупку, снабжение, подбор и применение оборудования. Коммерческий блок предназначен для технических специалистов, закупщиков и промышленных предприятий; он должен описывать уместный сценарий выбора/запроса предложения, не обещая неизвестных условий продажи.

Проверка ограничивает длину SEO-заголовка (до 70 символов) и описания (800–1200 символов), количество запросов (3–5) и отсеивает новые числовые значения в тексте. Структурированные характеристики и список пропусков формируются детерминированно из входа, а не поручаются модели. Для незаданного ожидаемого поля, пустого значения или `null` используется `данных нет`. Значения незаданного ожидаемого поля также показываются, а пустые производитель и описание отмечаются как недостающие в `missing_fields`.

Числовая проверка — эвристика по вхождениям цифр. Она не гарантирует семантическую достоверность каждого утверждения, корректность единиц, сохранение смысла параметра или отсутствие качественных галлюцинаций. Валидация структуры и промпт снижают риск, но каждый результат необходимо сверять с документацией конкретной модели и вручную просматривать перед публикацией.

## API и ключи

LLM-режим использует OpenAI-совместимый endpoint Chat Completions. Адрес, модель и ключ задаются через `OPENAI_BASE_URL`, `OPENAI_MODEL` и `OPENAI_API_KEY`; значения по умолчанию для адреса и модели — `https://api.openai.com/v1` и `gpt-4.1-mini`. Пример переменных находится в `.env.example`. Приложение не загружает `.env` автоматически.

Настройка `OPENAI_TIMEOUT` задаёт таймаут запроса в секундах (по умолчанию 30). Модель запрашивается в режиме JSON-объекта (`json_object`), а не в режиме JSON Schema / Structured Outputs. Ответ затем проверяется локально. Для структурных ошибок выполняется одна корректирующая генерация (до двух генераций на товар). Каждая генерация может выполнить до трёх сетевых попыток при временных HTTP-ошибках; таким образом, в верхнем пределе возможно до шести HTTP-запросов на товар. Для сравнения доступны [официальное руководство OpenAI по Structured Outputs](https://developers.openai.com/api/docs/guides/structured-outputs) и [документация GPT-4.1 mini](https://developers.openai.com/api/docs/models/gpt-4.1-mini).

Для доступа к реальному API нужен действующий ключ и сеть. В проверке CI используются тесты с подменённым транспортом и `--demo`; этот режим не имитирует успешный вызов модели и маркирует результат как демонстрационный. Отдельно пользователь выполнил реальную генерацию через `https://cheapvibecode.ru/v1` с моделью `gpt-6-luna`: обе карточки прошли структурную валидацию. Исходные результаты, редакторские замечания и пример после редактирования описаны в [live-check.md](live-check.md). Этот прогон подтвердил работоспособность интеграции с выбранным провайдером и продемонстрировал ограничение числовой эвристики: она пропускает неподтверждённые качественные утверждения.

## Состав демонстрационных данных

В `examples/inputs.json` находится один пример на основе предоставленного фрагмента PDF: «Манометр показывающий DM 02», производитель «Манотомь», диапазон 0–1,6 МПа, класс точности 1,5, присоединение G1/2, корпус 100 мм и описание назначения. Второй объект — явно синтетический неполный ввод датчика температуры; производитель и характеристики не предоставлены, технические значения не добавлены.

Эти примеры не являются двумя фактическими товарами из задания: в доступном фрагменте отсутствуют сведения о втором назначенном изделии. Перед публикацией следует заменить синтетический ввод полными исходными данными второго товара и проверить результат специалистом.

## Возможные дальнейшие улучшения

- Добавить оценку фактической точности и набор проверочных кейсов для поиска качественных галлюцинаций.
- Поддержать ссылки на источники для каждого факта и атрибуцию характеристик первичной документации.
- Расширить шаблоны и тестовые примеры на другие категории промышленного оборудования.
